# 连续模拟中日常 App 选择的记录与验证

同一小时可能先打开社交 App，再多次打开另一类 App。记录应能分别回答“先选了什么”和“哪类打开次数最多”。模型明确选择不用手机，以及模型没有给出可执行决定，也需要分别计数。

- [x] 用连续调用 `DigitalHelplessnessAgent.forward()` 的回归核对原始选择、当小时执行和下小时可见记忆，包括跨日、合法不用手机与技术失败。
- [x] 用旧十人归档重建昼夜、过去同小时活跃程度、当前有无任务的代表场景。保留原始覆盖数，另用标明来源的受控机会覆盖缺失的场景。
- [x] 让先导入口依次调用实际需求模块和计划模块。计划根据本次得到的需求重新生成候选渠道。按模块记录首答、修复、技术缺失和实际请求数。
- [x] 在五天验收里按人和日核对可执行计划、日常类别与活动次数、下小时读到的记录以及需求首答。以旧运行检验报告兼容性，保留旧失败。

完整十人五天的后两天共有 480 个人小时。先导的分层场景是独立测量，连续模拟的小时才会把实际执行写入下一小时。在两种验证中分别报告分母及运行范围。

公开汇总列有帮助方式配对、V7 连续运行和 V8 复测的数据与分母。V7 具有十人连续五天的轨迹，V8 的在线数据来自独立时点。[公开结果说明](../../../report/2026结项/仓库发布/2026-11-28/progress.md) · [机器可读数据](../../../report/2026结项/仓库发布/2026-11-28/progress.json)

本次 293 次日常使用全部查到了对应的首开类别、各类次数和小时导出。7 次在模拟的最后一小时。其余 286 次的首开类别及次数均与下一小时需求、计划两份实际输入匹配。第 5 天 00:00，十个人的计划都看到了前一日 23:00 的活动记录，其中 6 人前一小时选择日常 App，6 人均保留了首开。需求首答复述观察为 0 次，7 次需求重答后全部可用。

行为对照用十台设备同一日、同一小时的留出记录。460 个可比较小时中，参考设备在 91 个小时没有记录 App 活动，模拟在其中 2 个小时也没有活动，另外 89 个小时生成了活动。20 个模拟失败小时单列，其中 2 个对应设备无活动。模拟有额外安排的登录任务，设备使用者和合成人物也不同。这个对照显示当前模型生成手机活动过于频繁，不能从类别成功写入推导出使用节奏已经拟真。[连续运行的汇总与解释](../../../report/2026结项/仓库发布/2026-11-28/progress.md)

## 连续运行后的单点复测

小时计划 V8 的格式修复保留模型已经选中的行为、目标和评分。目标只有一个合法必需频道时，模型可在重答中补齐该频道。模型选择延期但给错时点时，可为同一目标重新选取菜单内的时点。取两类错误各自最早的一条实际首答复测，模型各用一次重答给出了有效行动。

对于第三类错误，最先尝试在观察中提醒人物距复查还有 17 小时。3 号人物第 5 天 07:00 的独立首答仍要求再次延期，校验按原规则拒绝。本轮共 3 次真实请求。所有复测独立归档，原轨迹仍为 460/480。

随后把等待时段的系统说明改为只介绍该小时真正可选的行动。预约继续保留，人物可以日常使用手机，也可以不用。取同一人物第 5 天 07:00、15:00、23:00 的固定状态，各发一次首答。三次都有效，均选择不用手机。其中 07:00 是前一轮已经问过的时点，15:00 和 23:00 在这次修改前没有单独复问过。这是同一人的三个独立时点，尚未逐小时推进新版轨迹。

最后，将完整五天的旧回答逐条送入当前版本，在原冻结状态上核对兼容性。460 个旧有效决定的行动、评分和使用次数一致，293 个日常首开的类别一致，原先的 20 个无效回答均保持为技术失败。

项目实验目录的全套离线回归为 782 项通过，有 3 条依赖弃用提示。使用项目 `agent_env` 解释器和本地 BM25 缓存。全套测试预加载真实 Qdrant、gRPC 和 fastembed，避免同一测试进程中的可选依赖替身影响原生检索集成测试。
